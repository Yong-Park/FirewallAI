# Security boundaries and invariants

Every change must preserve these invariants. Weakening any of them requires a new ADR that the human accepts. The threat model is in [../planning/07-security-model.md](../planning/07-security-model.md).

| ID | Invariant | Applies from | How it is enforced (planned) |
|---|---|---|---|
| SB-01 | v0.1 is **read-only**. No code path modifies firewall, network, or system configuration. | v0.1 | **Implemented (M1.1):** `tests/security/test_powershell_scripts.py` allows only read-only cmdlet allowlists and blocks forbidden constructs. Also code review and [AGENTS.md](../../AGENTS.md) §5 |
| SB-02 | The UI and AI processes **never run elevated**. The manifest uses `asInvoker`. | v0.1 | **Partly implemented (M1.1):** `collectors/windows/privilege.is_elevated()`; the CLI and GUI warn when elevated; an integration test asserts the tests run unelevated. **M1.5:** both packaged executables embed an `asInvoker` manifest with `uiAccess="false"` (verified by `packaging/verify_build.py`), and the frozen smoke tests assert the app reports `elevated: false` |
| SB-03 | Subprocess runs only through `powershell_runner`: absolute path, constant scripts, JSON over stdin, no `shell=True`, timeouts and output caps. **No `-ExecutionPolicy Bypass`, `-EncodedCommand`, or `-File`**; `PSModulePath` is restricted to system modules ([ADR 0009](../adr/0009-firewall-read-path.md) evidence §A). **Correction (M1.5 finding):** the runner passes only the System32 module path, but Windows PowerShell 5.1 itself inserts `%ProgramFiles%\WindowsPowerShell\Modules` ahead of it at start-up (observed on TE-1). That directory is admin-writable by default, the user-profile module path is not added, and the NetSecurity cmdlets load from System32. Pinning the modules by full path is an open decision. | v0.1 | **Implemented (M1.1):** `tests/security/test_powershell_runner.py` (fixed argv, injection corpus, timeout, output cap, `shell=False`, error classification); live round-trip in `tests/integration`; ruff `S` rules. **M1.3:** an opt-in JSON Lines streaming mode under the same rules, plus a strict line schema, per-line, total, and event-count caps, timeout, cancellation, and guaranteed child kill (`tests/security/test_streaming_runner.py`). Both modes: JSON nesting bombs are a structured `parse_error`, and stderr is drained with only 64 KiB kept, so it can never stall the child. **M1.5:** PyInstaller-specific environment values are never passed to PowerShell: `_PYI_*` and `_MEIPASS2` are always removed, and when frozen, `PATH`, `QT_PLUGIN_PATH`, and `QML2_IMPORT_PATH` entries pointing inside the (user-writable) bundle are removed. Nothing else is touched. Tested for normal and frozen execution (`tests/security/test_powershell_runner.py`) and against the frozen binary (`packaging/smoke`) |
| SB-04 | All external data is **untrusted** (rule names, descriptions, process names, paths, hostnames, logs, documents) and is validated at trust boundaries. | v0.1 | pydantic models; escaping tests |
| SB-05 | v0.1 makes **zero outbound network** connections. | v0.1 | **Implemented (M1.1):** `tests/conftest.py` makes any socket connection fail the test, and an import-linter contract forbids `socket`, `urllib`, `http`, and `ssl` in `firewallai`. **M1.5:** the packaged app excludes `ssl`, `http`, `urllib.request`, `asyncio`, `multiprocessing`, and other network clients; the bundle verifier asserts they are absent. Manual check before release |
| SB-06 | The AI **explains only**. It cannot execute commands, call privileged code, or modify state. Its output is schema-validated, and IDs and citations are checked against local data. | v0.2 | import-linter; validator tests; eval harness |
| SB-07 | The AI endpoint is **loopback by default**. A non-loopback or cloud endpoint requires explicit opt-in, consent per send, and redaction. | v0.2 | Settings validation; tests |
| SB-08 | No API keys or credentials in the repository, installer, logs, or database. Keys live only in Windows Credential Manager. | v0.1 | gitleaks; log-redaction tests |
| SB-09 | No model weights are bundled. Models come from Ollama under their own licenses. | v0.2 | Packaging check |
| SB-10 | Firewall changes need typed, allowlisted operations, a before/after diff, **explicit user approval**, drift detection, verification, an audit log, and rollback. | v0.4 | Helper-side validation; VM test matrix |
| SB-11 | Firewall write operations are tested **only in disposable VMs** until the safety exit criteria pass. | v0.4 | `FIREWALLAI_ALLOW_WRITES` + VM detection in dev builds |
| SB-12 | The LLM is **never** in a real-time packet or connection decision path. | v0.5 / research | Architecture review |
| SB-13 | No elevated component loads code from a user-writable directory. | v0.4 | Per-machine install for privileged components. **M1.5:** the portable folder is user-writable, so it must never contain or start an elevated component; both executables are `asInvoker` (verified) |
| SB-14 | Reports separate observed facts, evidence, AI interpretation, recommendations, and limitations. No compliance claims. | v0.1 | Report model types; template tests |
| SB-15 | Detection (collection, verdicts, findings, alerts) and any enforcement produce **identical outcomes** whether AI is enabled, disabled, unavailable, slow, or invalid. AI output is never an input to a detection or enforcement decision. ([ADR 0021](../adr/0021-hybrid-ai-orchestration.md)) | v0.1 (holds trivially), v0.2+ | Independence test (AI on, off, failing); import-linter (`core`, `collectors` never import `ai`) |
| SB-16 | `HOST_SENSITIVE` data **never** has standing cloud-upload permission. Each upload needs per-request authorization showing the exact payload and the destination provider. **No automatic cloud fallback.** ([ADR 0021](../adr/0021-hybrid-ai-orchestration.md)) | v0.2 | Unit and integration tests with a fake provider; payload-preview equals bytes sent |
| SB-17 | AI tasks have **no arbitrary shell, file-system, privileged, or network tools**. Only read-only lookups are allowlisted per task. Cloud calls go only through a restricted provider adapter, called by Python and not by the model, with **allowlisted endpoints** and user consent. ([ADR 0021](../adr/0021-hybrid-ai-orchestration.md)) | v0.2 | Tool-registry test (no forbidden tool types); adapter endpoint-allowlist tests; network allowlist test |
| SB-18 | **No definitive security verdict from incomplete evidence**, and **a missing filter never means "Any"/unrestricted**. Every rule filter is COLLECTED, NOT_COLLECTED (with a reason), or UNREADABLE (with an error). Unrecognized values are UNKNOWN tokens. Only `CompleteRuleEvidence` may feed a future verdict engine. (**Approved by the human, 2026-10-14.**) | v0.1 | **Implemented (M1.3):** `core.rules.FilterResult` validation, `core.evidence.evidence_for_verdict`, unit tests (`tests/unit/test_rule_collection.py`, `test_rule_models.py`), and Windows integration tests asserting no defaulted values and that every live rule with a non-`any` dynamic target/transport, dynamic keyword addresses, or a non-collected filter yields `IncompleteEvidence`. **M1.4 fix:** service and package filters keep `*` ("services only" / "app packages only"); M1.3 had mapped `*` to "any" (no live occurrences on TE-1; regression test in `tests/unit/test_correlation.py`). Endpoint process details use the same explicit-state pattern (`Observed`) |
| SB-19 | **No concurrent heavy firewall queries.** One rule collection at a time per process (`HEAVY_QUERY_LOCK`, BUSY otherwise), with detail queries sequential inside one PowerShell process (M1.2 evidence: parallel queries contend). (**Approved by the human, 2026-10-14.**) | v0.1 | **Implemented (M1.3):** collector lock; BUSY unit test; two-thread test asserting the second collection returns BUSY without invoking PowerShell and at most one run is active; single-flight GUI start test. **M1.4:** the endpoint snapshot uses a separate `ENDPOINT_SNAPSHOT_LOCK` and makes no firewall query; its one PowerShell call (`WIN32_SERVICES`, a light CIM query) may run while a rule scan runs |
| SB-20 | **Listener-to-firewall-rule correlation is descriptive only.** It never implies external reachability, never claims that an Allow rule permits a connection, and never raises a security finding solely because a port is listening. A rule is "related" only when every endpoint-identity filter (protocol, local port, dynamic port, program, package, service, owner, local address) matches; a known contradiction makes it "not related"; missing or ambiguous data or incomplete rule evidence makes it "cannot evaluate"; network-condition restrictions (profiles, interfaces, remote peers, IPsec/authorization) are listed as not evaluated, never dropped, and turn the result into a separate "related with unevaluated conditions" category, never a plain "related". Service-hosting ambiguity and app-container/package/owner scopes are "cannot evaluate". Process identity behind program/service matches is best effort. No rule scan is started automatically. (**Approved by the human, 2026-10-15.**) | v0.1 | **Implemented (M1.4):** `core.correlation` (`relate`, `RuleIndex`); truth-table tests (`tests/unit/test_correlation.py`); forbidden-claim wording tests over correlation text, CLI output, and GUI text (`tests/unit/test_correlation.py`, `tests/security/test_endpoint_collector_security.py`, `tests/ui/test_network_tab.py`); a GUI test asserting no rule scan starts automatically; live integration test (`tests/integration/test_windows_endpoints.py`) |
